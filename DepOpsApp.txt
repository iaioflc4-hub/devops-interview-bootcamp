# PROJECT: DEVOPS INTERVIEW BOOTCAMP — AI-POWERED INTERACTIVE LEARNING PLATFORM

## 1. ROLE AND OBJECTIVE

Act as a Senior Software Architect, Full-Stack Developer, DevOps Engineer, Instructional Designer, and AI Learning Systems Engineer.

Your mission is to design and develop a complete, functional, interactive DevOps training platform focused on preparing a technology-oriented learner with basic technical knowledge but limited professional DevOps experience to perform successfully in Junior DevOps, Trainee DevOps, Cloud Engineer, Infrastructure Engineer, and DevOps Support interviews.

This must NOT be a static educational website, a collection of articles, or a simple flashcard application.

Build an interactive learning environment that combines:

1. Structured technical training.
2. Adaptive AI tutoring.
3. Spaced repetition.
4. Hands-on laboratories.
5. Interactive terminal and shell exercises.
6. Real computer-based assignments.
7. Automated exercise validation.
8. Technical interview simulations.
9. Progress tracking and performance analytics.
10. Personalized learning recommendations.

The system must teach through active practice, not passive reading.

## 2. LEARNER PROFILE

Design the learning experience around this profile:

- Technical knowledge: intermediate.
- DevOps knowledge: beginner.
- Technology aptitude: high.
- Learning speed: high.
- Programming knowledge: limited/intermediate.
- Cybersecurity fundamentals: basic knowledge.
- Operating system: Windows 11.
- Available hardware: Intel Core i5 10th Generation, 8 GB RAM.
- Primary working environment: Windows with WSL2 and Ubuntu.
- Study availability: 2–3 hours per day.
- Intensive preparation period: 4 days.
- Main objective: maximize technical interview readiness in a very short time.
- Budget: preferably free and open-source tools.

Avoid assuming advanced programming knowledge. Explain unfamiliar concepts progressively, but do not oversimplify technical content.

## 4. SPACED REPETITION ENGINE

Implement a genuine spaced repetition system.

Do not simply show the same questions every day.

Each learning concept must have:
- Unique ID.
- Topic and subtopic.
- Difficulty.
- Initial explanation.
- Practical example.
- Interview question.
- Expected answer.
- Common misconceptions.
- Related concepts.
- Review history.
- Confidence score.
- Next review date.

Use an SM-2-inspired scheduling algorithm or FSRS if practical.

The system should schedule reviews based on:
- Correctness.
- Response time.
- Confidence.
- Number of previous reviews.
- Difficulty.
- Previous mistakes.

Suggested review buttons:
- Again.
- Hard.
- Good.
- Easy.

Implement:
- Daily review queue.
- Overdue reviews.
- Weak topic detection.
- Review calendar.
- Retention statistics.
- Automatic prioritization.

IMPORTANT: Since the preparation lasts only four days, implement short learning intervals as well as longer intervals:

- Initial exposure.
- 20 minutes later.
- Next study session.
- Next day.
- 48 hours later.
- Final interview simulation.

If a concept is answered incorrectly, explain the error and schedule an earlier review.

Use active recall rather than showing answers immediately.

## 5. INTERACTIVE TUTOR

Build an AI tutor that behaves like a technical instructor.

The tutor must:

1. Explain concepts progressively.
2. Use analogies when helpful.
3. Give practical examples.
4. Ask questions one at a time.
5. Wait for the learner's answer.
6. Evaluate technical accuracy.
7. Detect misconceptions.
8. Explain why an answer is wrong.
9. Provide hints before revealing solutions.
10. Adapt difficulty according to performance.
11. Generate follow-up questions.
12. Recommend additional exercises.

The tutor must distinguish between:
- Knowing a definition.
- Understanding a concept.
- Being able to implement it.
- Being able to troubleshoot it.
- Being able to explain it in an interview.

Do not mark a concept as mastered merely because the learner read its explanation.

## 6. HANDS-ON LABORATORY ENGINE

This is one of the most important requirements.

The application must include a laboratory environment where the learner performs actual technical tasks.

Implement three laboratory modes.

### MODE A — Embedded terminal

Provide an interactive Linux shell.

Preferred implementation:
- Real Ubuntu environment through WSL2.
- Alternatively, an isolated Linux container.
- Optional lightweight simulated terminal for introductory exercises.

The terminal should support:
- Command input.
- Command history.
- Output display.
- Multiple commands.
- Error messages.
- Copy/paste.
- Reset environment.
- Exercise-specific working directories.

Never simulate successful command execution when no real execution occurred.

### MODE B — Guided computer assignments

The system must instruct the learner to perform actions directly on their own computer.

Example:

MISSION: Investigate a Linux service.

1. Open your Ubuntu terminal.
2. Execute `systemctl status ssh`.
3. Identify whether the service is active.
4. Execute `journalctl -u ssh -n 20`.
5. Identify the latest relevant log entries.
6. Return to the training application.
7. Submit your findings.

The platform must validate the submitted results or command output.

Other missions should include:
- Creating a Linux user.
- Changing permissions.
- Finding large files.
- Inspecting network connections.
- Building Docker images.
- Running containers.
- Creating Git branches.
- Editing YAML files.
- Configuring CI/CD pipelines.

### MODE C — Troubleshooting simulations

Create realistic environments with intentional failures.

Examples:
- Nginx is not responding.
- Container exits unexpectedly.
- Application cannot resolve DNS.
- Disk usage reaches 100%.
- Incorrect file permissions prevent execution.
- Docker container cannot reach another service.
- CI pipeline fails during testing.
- Kubernetes Pod enters CrashLoopBackOff.

The learner must diagnose the problem and provide a solution.

The platform should evaluate:
- Correct commands.
- Diagnostic sequence.
- Root cause.
- Final resolution.
- Explanation of the solution.

## 7. SAFETY AND LOCAL COMPUTER EXECUTION

The application may interact with the learner's computer, but execution must be secure.

Requirements:
- Never execute arbitrary AI-generated commands without explicit user approval.
- Show commands before execution.
- Separate read-only commands from modifying commands.
- Require confirmation for destructive operations.
- Restrict execution to designated laboratory directories and isolated environments.
- Never expose host credentials, SSH private keys, API keys or environment secrets.
- Never execute commands with administrator privileges automatically.
- Provide reset and cleanup functions.
- Log laboratory activity.
- Prefer WSL2 or disposable Docker containers.

Use a local backend or controlled terminal bridge if required.

Do not assume a browser-only application can directly access the user's operating system shell.

If direct execution is unavailable, provide a clearly identified manual terminal mode with instructions and result validation.
